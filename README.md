# Сводная отчётность по котельным: ЛЭРС УЧЁТ + 1С + бот MAX

Сервис по ТЗ заказчика (ООО ИЦ «Теплосфера»):

* раз в неделю опрашивает **суточные архивы** в «ЛЭРС УЧЁТ» по 56 точкам учёта из перечня;
* раз в месяц забирает **затраты по объектам** из 1С;
* сводит всё в **Excel-таблицу** формы из ТЗ и считает **КПД котельной**;
* значения КПД ниже 80 % подсвечивает красным;
* присылает готовый файл **ботом в мессенджере MAX** — по расписанию и по команде.

Данные каждого успешного опроса складываются в локальную базу SQLite, поэтому
повторный запуск не теряет уже выгруженные показания, а планировщик не рассылает
дубли отчётов после перезапуска.

---

## Быстрый старт

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows;  Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env             # Linux/macOS: cp .env.example .env — затем заполнить ключи
python -m app.main --check         # проверить связь с ЛЭРС и 1С
python -m app.main --once week     # собрать отчёт за прошлую неделю
python -m app.main                 # боевой режим: бот + расписание
```

Демонстрационный файл на реальном перечне объектов и тестовых показаниях
(боевые источники не нужны):

```bash
python tools/make_demo.py
```

## Переменные окружения (.env)

Полный список — в [.env.example](.env.example). Ключевые группы:

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LERS_BASE_URL` | адрес сервера ЛЭРС | `http://109.201.97.4:10000` |
| `LERS_API_KEY` | ключ приложения (заголовок `x-lers-api-key`) | пусто |
| `LERS_RETRIES`, `LERS_RETRY_BASE_DELAY` | ретраи на 429/5xx/таймаут | `4`, `1.0` |
| `ONEC_MODE` | `manual` / `odata` / `http` | `manual` |
| `MAX_BOT_TOKEN` | токен бота (заголовок `Authorization`) | пусто |
| `MAX_BROADCAST_CHAT_IDS` | чаты рассылки по расписанию | пусто |
| `MAX_ALLOWED_USER_IDS` | кому разрешены команды (пусто = всем) | пусто |
| `GAS_CALORIFIC_KCAL` | теплотворность газа, ккал/Нм3 | `8200` |
| `EFFICIENCY_THRESHOLD` | порог подсветки КПД, % | `80` |
| `DB_PATH` | файл SQLite-состояния | `data/archive.sqlite3` |
| `TZ_NAME` | часовой пояс расписания | `Europe/Moscow` |

**Секреты (`LERS_API_KEY`, `LERS_PASSWORD`, `ONEC_PASSWORD`, `MAX_BOT_TOKEN`) держатся
только в `.env` или в переменных окружения среды деплоя.** В коде и в git их нет,
в логах они маскируются (`app/logging_utils.py`). Файл `.env` в `.gitignore`.

## Команды бота

```
/start, /help                        справка
/report week                         отчёт за прошедшую неделю (суточные архивы ЛЭРС)
/report month                        отчёт за прошедший месяц (тепло + затраты 1С)
/report 2026-07-01 2026-07-31        отчёт за произвольный период
/status                              состояние ЛЭРС и 1С + время последнего успешного опроса
```

Если задан `MAX_ALLOWED_USER_IDS`, команды выполняются только для этих пользователей,
остальным бот вежливо отказывает. По расписанию отчёты приходят сами: недельный —
по понедельникам, месячный — в начале месяца (настраивается в `.env`).

## Расчёт КПД

В ТЗ формула записана как `тепло / (газ × 8200)`. В таком виде она не даёт процентов:
тепло измеряется в Гкал, а произведение «газ × теплотворность» — в ккал. В отчёте
формула приведена к одной размерности (1 Гкал = 10⁶ ккал):

```
КПД, % = Q[Гкал] / (V[Нм3] × ТеплотвГаза[ккал/Нм3] / 1 000 000) × 100
```

КПД в Excel лежит **формулой**, а не готовым числом. Теплотворность (ячейка B3,
именованный диапазон `ТеплотвГаза`) и порог подсветки (ячейка B4, `ПорогКПД`)
меняются прямо в файле — все КПД пересчитываются, подсветка перенастраивается,
код править не нужно.

## Подключение ЛЭРС УЧЁТ

Авторизация — заголовок `x-lers-api-key` ([docs.lers.ru/dev/rest](https://docs.lers.ru/dev/rest/)).
Ключ выпускается в карточке пользователя, вкладка **«Приложения»**. Полный перечень
методов конкретного сервера доступен по адресу `http://<сервер>:10000/api/swagger`.

Между версиями ЛЭРС пути к суточным данным отличаются, поэтому `lers_client.py`
при первом успешном запросе подбирает рабочий маршрут из списка кандидатов и
запоминает его в `data/lers_routes.json`. Обновление сервера заказчика не потребует
правок кода — максимум сброса этого файла.

Диагностика:

```bash
python tools/probe_lers.py            # связь + сопоставление 56 точек по номерам
python tools/probe_lers.py --point 39 # выгрузка суток по одной точке + сырой JSON
```

Типичные причины отказа: порт 10000 закрыт снаружи (ЛЭРС по умолчанию слушает
только локальную сеть), ключ не выпущен, у учётной записи нет прав на объекты.

## Подключение 1С

Режим задаётся `ONEC_MODE`:

| Режим | Когда использовать | Что нужно от заказчика |
|---|---|---|
| `manual` | по умолчанию, пока нет доступа | файл `data/costs.xlsx`: «Объект», «Затраты» |
| `odata` | штатный интерфейс 1С | публикация базы на веб-сервере, пользователь с правом на OData |
| `http` | **рекомендуется** для этой базы | HTTP-сервис 1С, отдающий JSON за период |

> Важно: на боевой базе затраты берутся из виртуальной таблицы
> `РегистрБухгалтерии.Хозрасчетный.ОборотыДтКт`, которую **стандартный OData не
> отдаёт**. Рабочий вариант — режим `http` с небольшим HTTP-сервисом 1С. Готовый код
> сервиса и шаги публикации: [docs/1c_http_service.md](docs/1c_http_service.md).

Наименования объектов в ЛЭРС и статей затрат в 1С не совпадают дословно (проверено
на боевых данных — авто‑сопоставление по названиям ловит лишь малую часть). Надёжное
решение — **таблица соответствий** `data/costs_mapping.xlsx` (две колонки: «Название
в 1С», «Номер котельной ЛЭРС»). Путь задаётся `ONEC_MAPPING_FILE`. Затраты сначала
раскладываются по номерам котельных из этой таблицы, а для строк без соответствия
работает запасное сопоставление по названию (`onec_client.match_costs`).
Несопоставленные строки видны в колонке «Примечание».

## Подключение бота MAX

Актуальные требования платформы ([dev.max.ru/docs-api](https://dev.max.ru/docs-api)):

* запросы идут на домен `platform-api2.max.ru`;
* токен передаётся заголовком `Authorization` — query-параметр больше не поддерживается;
* лимит 30 запросов в секунду;
* создавать и публиковать ботов могут только верифицированные юрлица РФ —
  **токен получает заказчик** в разделе «Чат-боты» на business.max.ru;
* файл отправляется в два шага: `POST /uploads?type=file` → загрузка по полученному URL →
  токен вложения в `POST /messages`. Между загрузкой и отправкой нужна пауза,
  иначе сервер отвечает `attachment.not.ready` (обработано ретраями).

Для получения обновлений используется long polling (`GET /updates`). Цикл polling
устойчив к сбоям: ошибка отдельного запроса логируется, опрос продолжается.
Документация MAX рекомендует для production webhook (`POST /subscriptions`) с
HTTPS-сертификатом — переключение отдельная задача, требующая домена с валидным
сертификатом.

`chat_id` для рассылки по расписанию узнаётся один раз: добавить бота в рабочий чат
и посмотреть `chat_id` в логе события `bot_added`, затем прописать в `MAX_BROADCAST_CHAT_IDS`.

### TLS-сертификат MAX (Russian Trusted CA)

Сертификат `*.max.ru` выпущен **«Russian Trusted Root CA»** (Минцифры). Этого корня
нет в стандартном наборе `certifi`, поэтому без него проверка сертификата падает с
`CERTIFICATE_VERIFY_FAILED`. Официальные корневой и промежуточный сертификаты лежат
в `data/certs/` и автоматически добавляются к доверенным (см. `MAX_CA_BUNDLE`,
`MAX_VERIFY_SSL` в `.env`). Проверка TLS при этом **не отключается**. Обновить корни
(если Минцифры перевыпустит) можно из официального источника
[gu-st.ru](https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt), заменив
файлы в `data/certs/`.

> Связь с ботом проверена на боевом API: `GET /me` вернул бота «ЛЭРС-2026»
> (`@id3305718345_bot`). Домен, авторизация заголовком и TLS с Russian CA — рабочие.

## Развёртывание на Amvera

Сервис — бот + планировщик и лёгкий health-эндпоинт на `containerPort` (его
проверяет Amvera). Сборка идёт по [Dockerfile](Dockerfile) (`python:3.11-slim`,
часовой пояс `Europe/Moscow`). Конфигурация — [amvera.yml](amvera.yml).

1. Зарегистрироваться/войти на [amvera.ru](https://amvera.ru), создать проект
   (кластер Варшава), тип — **Docker** / «Через Git».
2. Залить код одним из способов:
   * подключить GitHub-репозиторий проекта, **либо**
   * добавить git-remote Amvera и запушить:
     ```bash
     git remote add amvera https://git.amvera.ru/<логин>/<проект>
     git push amvera main
     ```
3. В панели создать **постоянное хранилище** и примонтировать на `/data`
   (там живут `archive.sqlite3` и готовые отчёты `out/`). Это уже указано в
   `amvera.yml` (`persistenceMount: /data`).
4. В панели Amvera → **Переменные окружения** задать секреты (в `amvera.yml` и в
   git их НЕТ):
   * `MAX_BOT_TOKEN` — токен бота MAX;
   * `LERS_API_KEY` — ключ ЛЭРС (при недоступности ключа — `LERS_LOGIN` + `LERS_PASSWORD`);
   * при выдаче 1С: `ONEC_MODE=odata` (или `http`), `ONEC_BASE_URL`,
     `ONEC_USERNAME`, `ONEC_PASSWORD`.
   Остальное (`TZ`, `DB_PATH=/data/archive.sqlite3`, `OUTPUT_DIR=/data/out`,
   `ONEC_MODE=manual`, `LOG_LEVEL`) уже зашито в образ по умолчанию.
5. Задеплоить. В логах должно появиться «Health-сервер слушает порт 80»,
   «Бот запущен…» и строка расписания.

Локальная проверка сборки образа:

```bash
docker build -t kotelnaya .
docker run --rm --env-file .env -v "%cd%/data:/data" kotelnaya python -m app.main --check
```

> На постоянном томе `/data` держатся `archive.sqlite3` и папка `out/`. Файл
> `data/points.xlsx` зашит в образ (это перечень заказчика); если он должен
> обновляться без пересборки — вынести его на том тоже.

Альтернатива облаку — systemd-юнит на сервере заказчика: нужен доступ к ЛЭРС и 1С
по локальной сети, Python 3.11+, исходящий HTTPS на `platform-api2.max.ru`.

## Что делать, когда придут доступы

**Токен бота MAX** (заводит заказчик):
1. Вписать `MAX_BOT_TOKEN` в `.env` / переменные окружения Amvera.
2. Добавить бота в рабочий чат, узнать `chat_id`, вписать `MAX_BROADCAST_CHAT_IDS`.
3. При необходимости ограничить круг — заполнить `MAX_ALLOWED_USER_IDS`.
4. Запустить `python -m app.main`; отправить боту `/status` и `/report week`.

**Ключ ЛЭРС / открытие порта**:
1. Вписать `LERS_API_KEY` (или `LERS_LOGIN`/`LERS_PASSWORD`).
2. `python tools/probe_lers.py` — убедиться, что связь есть и точки сопоставились.
3. При несовпадении маршрута удалить `data/lers_routes.json` и повторить.

**Доступ к 1С**:
1. Поставить `ONEC_MODE=odata` (или `http`), заполнить `ONEC_BASE_URL`,
   `ONEC_USERNAME`, `ONEC_PASSWORD`.
2. Уточнить и при необходимости поправить `ONEC_ODATA_RESOURCE`,
   `ONEC_FIELD_OBJECT`, `ONEC_FIELD_AMOUNT` (см. `app/onec_client.py`).
3. `python -m app.main --check` — проверить, что затраты подтягиваются.
4. Согласовать таблицу соответствий «объект ЛЭРС ↔ статья затрат 1С».

## Открытые вопросы к заказчику

1. **Методика КПД по котельной.** Проверено на боевом сервере: точки перечня —
   раздельные (каждая либо тепло, либо газ), парных «тепло+газ» в одной точке нет.
   На сервере у каждой точки есть `nodeId` (котельная), поэтому КПД логично считать
   по котельной: сумма тепловых точек узла / газовый узел того же `nodeId`.
   **Нужно подтверждение методики** — после этого включаем агрегацию по `nodeId`
   в `report.build_report`.
2. **8200 ккал/Нм3** — низшая или высшая теплотворная способность, по какому документу.
   В ТЗ единица расхода указана как «Нм3/ч» (мгновенный расход); для КПД за период
   нужен объём за период, поэтому в отчёте колонка в Нм3.
3. **Соответствие объектов** ЛЭРС ↔ статей затрат 1С: нужна таблица соответствий
   либо общий код объекта.
4. **Доступ к 1С**: адрес базы, учётная запись, имя регистра/отчёта с затратами
   по котельным.

Эти пункты продублированы на листе «Методика и примечания» каждого отчёта и в выводе
`python -m app.main --check` — как явные предупреждения, а не как «нет данных».
```
